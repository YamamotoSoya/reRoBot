# Knowledge Check

Claude が書いたコードの設計判断をユーザに解説し、対話クイズで理解を確認したうえで、
記録を `docs/claude/knowledge/` に保存する。目的は「動くが中身を説明できないコード」を
リポジトリに増やさないこと。

## いつ使うか

- Claude が非自明な実装・修正を完了した直後 (数行の typo 修正などは対象外)
- ユーザが「説明して」「クイズ出して」「理解確認したい」等と要求したとき
- 過去に Claude が書いた既存コードをユーザが「読めるようになりたい」と言ったとき

1 回 = 1 テーマ。複数の独立した変更をまとめて出題しない (混ざると弱点が特定できない)。

## 手順

1. **対象を特定**する。直近セッションの diff (`git diff` / `git log -p -1`) か、ユーザ指定の
   ファイル・機能。対象コードは必ず読み直してから出題する (記憶で出題しない)。

2. **解説パート**。以下の 4 点を構造化して説明する。ユーザは「なぜそうなるか」まで
   求める (PROJECT_STATE §9)。動作説明だけで終わらせない:
   - **何をしたか**: 変更の全体像とデータの流れ
   - **なぜこの方法か**: 選んだ根拠 (制約・既知の罠・性能)
   - **却下した代替案**: 他にどんな書き方があり、なぜ選ばなかったか
   - **踏みやすい罠**: この部分を将来触るとき何に注意すべきか

3. **クイズパート**。理解確認の質問を 3〜5 問、**1 問ずつ**出題する (まとめて出さない)。
   ユーザの回答は自由記述で受け、回答ごとに正誤 + 補足を返す:
   - 「コードを読まないと答えられない問題」を最低 1 問含める
     (例: 「この値を 2 倍にしたら実機で何が起きるか」「この行を消すとどの症状が出るか」)
   - このプロジェクト固有の罠 (CiA402 逐次発行、`ros__parameters`、スケーリング等) に
     絡む変更なら、その罠を問う問題を優先する
   - 全問終了後、正答できなかった論点を要約する

4. **文書化**する。同階層の `template.md` を
   `docs/claude/knowledge/<YYYY-MM-DD>_<slug>.md` にコピーし、Edit ツールで埋める。
   `<slug>` は対象コンポーネント + テーマの英小文字 snake_case
   (例: `epos4_controller_init_sequence`)。

   ```sh
   mkdir -p docs/claude/knowledge
   cp .claude/skills/knowledge-check/template.md \
      docs/claude/knowledge/$(date +%Y-%m-%d)_<slug>.md
   ```

   初回実行時は `docs/claude/PROJECT_STATE.md` §8 の docs 地図に
   `docs/claude/knowledge/` の行を 1 行追記する。

5. **完成したパスをユーザに報告**し、弱点メモに書いた論点を次回復習対象として一言添える。

## 命名規則

- ファイル名: `YYYY-MM-DD_<slug>.md`
- `<slug>` は英小文字 snake_case で、対象コンポーネント + テーマ
  (`epos4_odometry_heading_integration`, `bus_yml_pdo_scaling` など)

## 守るべきこと

- **クイズは減点でなく補強が目的**。間違いを責める書き方をしない。正答でも根拠が
  曖昧なら補足する。
- **答えを先に言わない**。解説パートで出題予定の論点を全部説明してしまうと確認に
  ならない。解説は設計判断中心、クイズは挙動・因果中心に分ける。
- **ユーザの回答を改変しない**。記録には回答の要旨をそのまま残す (正解に寄せて
  書き直さない)。弱点メモの価値はここで決まる。
- 出題前に対象コードを読み直す。**コードと食い違う出題・解説は最悪の結果**
  (誤った知識が定着する)。
