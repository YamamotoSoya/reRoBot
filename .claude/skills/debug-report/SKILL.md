# Debug Report

セッション中に判明した不具合・調査ログ・修正をまとめた振り返り資料を `docs/report/` 配下に保存する。

## いつ使うか

- 詳細な切り分け作業を経てバグを修正した直後
- 再発防止のために手順・根拠を残しておきたいとき
- ユーザが「レポートにまとめて」「docs/report に残して」等と要求したとき

1 レポート = 1 課題。複数同時に起きた問題は別ファイルに分割する (横断的なまとめが必要なときだけ追加で 1 本作る)。

## 手順

1. **対象セッションの内容を整理**する。本セッションで報告対象にする問題を 1 件に絞る。複数候補があれば優先度をユーザに確認する。

2. **必須情報を収集**する。テンプレートを埋めるため、以下を取得する:
   - 日付 (環境の `currentDate` または `date +%Y-%m-%d`)
   - ブランチと HEAD: `git rev-parse --abbrev-ref HEAD` / `git log -1 --oneline`
   - 関連ファイルパス (修正・参照したもの)
   - 症状を再現するコマンドと実ログ抜粋
   - 切り分け過程で取った計測値・コマンド出力
   - 修正内容 (diff か該当コードブロック)
   - 修正前/後の検証結果

3. **テンプレートをコピー**する。同階層の `template.md` を `docs/report/<YYYY-MM-DD>_<slug>.md` にコピーする。`<slug>` は影響コンポーネント + 症状を表す英小文字 snake_case (例: `slam_toolbox_scan_queue_full`)。

   ```sh
   cp .claude/skills/debug-report/template.md \
      docs/report/$(date +%Y-%m-%d)_<slug>.md
   ```

   同日に複数本ある場合は末尾に `_2`, `_3` を付ける。

4. **Edit ツールで埋める** (Write での丸ごと上書きは禁止 — テンプレ構造を保つため)。
   - `<...>` プレースホルダはすべて置換する。
   - 該当しないセクションは削除せず「該当なし」と明記する (将来読む人が「書き忘れ」と「無い」を区別できるように)。
   - 数値・ログ・コマンドは原文ママを優先。**観測していない値を捏造しない**。未計測なら実行して埋めるか「未計測」と書く。
   - コードブロックには言語識別子 (` ```yaml `, ` ```bash `, ` ```cpp ` 等) を付ける。

5. **完成したパスをユーザに報告**する。一文でレポートのレビューを促す。

## 命名規則

- ファイル名: `YYYY-MM-DD_<slug>.md`
- `<slug>` は英小文字 snake_case で、影響コンポーネント + 症状を端的に (`slam_toolbox_scan_queue_full`, `epos4_controller_init_homing_fail` など)
- タイトル行は日本語可。問題の主体と症状が一目でわかる形にする

## 守るべきこと

- **観測事実と推測を混ぜない**。「実測値: …」「推測: …」と書き分ける。
- **修正の "なぜ" を必ず残す**。値や手法を選んだ根拠が無いレポートは、半年後に読み直したとき改修できない。
- **教訓セクションを省略しない**。1 行でも良いので必ず書く。再発防止の核。
- 機微情報 (トークン・社内ホスト名等) はそのまま貼らない。マスキングする。
