# Feature Doc

追加・移植した機能の設計文書を `docs/features/` 配下に保存する。debug-report が
「壊れた→直した」の記録なのに対し、こちらは「作った→なぜこう作ったか」の記録。

## いつ使うか

- 新機能・新ノード・移植 (ROS1→ROS2 等) の実装が一区切りついた直後
- ユーザが「features に残して」「設計文書を書いて」等と要求したとき

1 文書 = 1 機能。既存機能の不具合修正は debug-report スキルを使う (棲み分け)。

## 手順

1. **対象機能を確定**する。維持した機能・意図的にスコープ外にしたものを列挙できる
   状態にする (ここが曖昧なら実装内容を読み直す)。

2. **必須情報を収集**する:
   - 日付・対象パッケージ・対象 ROS ディストリビューション
   - 設計判断とその根拠 (なぜこの方式か、代替案の却下理由)
   - データフロー (トピック名・サービス名・メッセージ型は実物から転記)
   - 起動・使用コマンド (実際に動かしたものをそのまま)
   - 変更・追加したファイル一覧
   - 既知の制限・未対応事項

3. **テンプレートをコピー**する。同階層の `template.md` を
   `docs/features/<YYYY-MM-DD>_<slug>.md` にコピーする。`<slug>` は機能を表す
   英小文字 snake_case (例: `motor_free_mode`, `rfans_driver_ros2_port`)。

   ```sh
   cp .claude/skills/feature-doc/template.md \
      docs/features/$(date +%Y-%m-%d)_<slug>.md
   ```

4. **Edit ツールで埋める** (Write での丸ごと上書きは禁止 — テンプレ構造を保つため)。
   - `<...>` プレースホルダはすべて置換する。
   - 該当しないセクションは削除せず「該当なし」と明記する。
   - トピック名・パラメータ名・コマンドは実物から転記。**記憶で書かない**。
   - 設計の勘所は最重要のものから番号順に並べる。

5. **完成したパスをユーザに報告**する。関連する docs/issue・docs/report があれば
   相互リンク (相対パス) を張ったことも報告する。

## 命名規則

- ファイル名: `YYYY-MM-DD_<slug>.md`
- `<slug>` は英小文字 snake_case で機能を端的に
- タイトル行は日本語可。何の機能か一目でわかる形にする

## 守るべきこと

- **観測事実と設計判断を書き分ける**。「実測: …」「判断: …」を混ぜない。
- **「なぜこう作ったか」を必ず残す**。半年後に改修する人 (未来の自分・別の Claude) が
  同じ検討をやり直さないための文書。
- **スコープ外を明記する**。「やっていないこと」が書いていない文書は、読む側が
  実装漏れと意図的な除外を区別できない。
- 機微情報 (トークン・社内ホスト名等) はマスキングする。
