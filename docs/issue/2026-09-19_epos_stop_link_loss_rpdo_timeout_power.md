## 1. ユーザ報告 (原文要約)

1. 5号館 2 周 bag 収録 → バッテリ交換。この時点では 0.5 m/s 急発進・段差ともに問題なし。
2. 交換後、アスファルトのわずかな段差で停止 (赤)。再起動して走行再開 → 反射板の 2 cm 段差を越えた後に**暴走** (コントローラを受け付けず止まらない) → 非常停止で電源遮断。以後、わずかな段差・急発進・急停車で頻繁に停止。
3. 帰着後: EPOS 緑点滅 (Disabled) だが launch の瞬間に赤 → 「非常停止スイッチが壊れていた」ことが判明、修理。
4. 再現実験 (joy、足でタイヤに負荷): (1) 負荷中は EPOS・DSR とも緑。足を離すと joy と無関係に止まらず、launch 側にエラー → 非常停止で赤。(2) 電源再投入後、低速 (~0.1) は問題なし、一気に 0.5 m/s で EPOS 赤・モータ停止、DSR 緑。(3) さらに再起動後は「どれだけ急な指令・負荷でも止まらない」→ 数分後に「止まった。EPOS 赤、モータ停止、指令が効かない」。

## 6. 構造的な問題 (原因が何であれ効く対策の根拠)

1. **通信断で止まらない層がある (確定)**: EPOS 側は 10 ms の RPDO timeout (0x8250 → quick stop) で守られるが、**PDO が届き続ける形の故障** (受信側のみ喪失・パッド喪失) では `epos4_controller` が最後の指令を無期限に送り続ける。joy_node はデバイス喪失時にゼロ Joy を出さず publish 停止 (ros-drivers/joystick_drivers `handleJoyDeviceRemoved`)、teleop_twist_joy は Joy 受信時のみ publish。EPOS 側 consumer heartbeat (0x1016) はこの型 (TX 生存) には無効。
2. **フォルトコードが残らない運用 (確定)**: ros2_canopen は EMCY を `/diagnostics` にしか流さない (端末に出ない)、0x1003 は電源断で消える、boot SDO が毎起動 Fault reset。今日、主電源を切った 2 回 (15:00, 15:04) でコードを失った。**非常停止のみ (ロジック直結で生きる) → 0x1003:01〜05 読み → 電源断** の順に変える。
3. **can0 再作成を master が追従しない (確定)**: `can0 (unregistered)` 後に canusb-up.service が can0 を再作成しても lely は旧 ifindex に張り付く (15:35:11〜15:49 で実証)。「can0 UP = 正常」判定は無効 (08-11 の教訓の再確認)。
4. **モータ電源容量 (候補 H5 だが設計として要見直し)**: RSD-60L-24 ×2 = 120 W に対し EPOS 2 台の Max output current 10 A × 24 V = 480 W 級のピーク要求。折り返しが実証されなくても設計マージンが無い。
5. **0x60C2 = sync = 10 ms でマージン 0** (H1)。0x6077 (torque) の SDO ポーリング (~10 Hz × 2 ノード) が常時走りバス/slcan 負荷を上げている (PDO 未マップのため)。

## 7. 次の一手 (安い順・判別力順)

1. **常時 `candump -ta -l can0` を回してから走行** (0 円)。(i) EPOS の EMCY フレーム (0x081/0x082) に error code が乗るので電源断で失われない、(ii) EPOS フォルトとリンク死の順序がミリ秒で決まる、(iii) SDO timeout 中に TPDO/heartbeat が見えれば H3、SYNC/RPDO (loopback) はあるが EPOS 側フレームが無ければ H2/USB、両方無ければ TX 死。赤になったら**電源を切る前に** 0x1003:01〜05 を読む:

### 10.2 副産物: USB 再列挙直後の slcand 起動競合 (2/2 再現、手動 restart で毎回復帰)

- 15:35:10〜11 と 17:16:00 の両方で、`FTDI … attached to ttyUSB0` と `slcand: starting on TTY` が**同一秒**。できた can0 は UP・送信カウンタは増えるが**受信 0** (heartbeat も届かない)。`sudo systemctl restart canusb-up.service` で毎回受信が戻る (15:45、17:2x)。
- 解釈 (本命): udev の `SYSTEMD_WANTS` で列挙の瞬間に service が起動し、FTDI が応答できる前に slcand の `C` / `S8` / `O` が流れてアダプタの CAN チャネルが開かない。slcand は応答を検証しないので can0 は UP になる。

- 対策: README の unit 定義に `ExecStartPre=/bin/sleep 2` を追加 (実機 `/etc/systemd/system/canusb-up.service` への反映は sudo が要るためユーザ作業。`daemon-reload` 後、抜き差しで検証)。`scripts/can_up.sh` に「3 s 間 送信あり・受信ゼロ → service 再起動」を追加 (09-19)。

### 10.6 19:25 事象のアダプタ直接診断 (19:50、slcand 停止中に tty へ LAWICEL コマンドを直接送信) — **アダプタ内部リセットで確定**

| コマンド | 応答 | 意味 |
|---|---|---|
| `V` | `V1011` | ファーム生存 (HW 1.0 / FW 1.1) |
| `F` (status) | BELL (0x07) | エラー = チャネルが**閉じている** |
| `C` (close) | BELL | 既に閉 |
| `O` (open) | BELL | **ビットレート未設定**で open 不可 |
| `S8` → `O` | CR, CR | 1 Mbps 設定 → open 成功 |
| `F` | `F00` | エラーフラグ無し (バスオフでも error passive でもない) |
| `t60184001100000000000` (SDO read 0x1001 → node 1) | `z` + `t58184F01100000000000` | 送信 ACK + EPOS 応答 (0x1001 = 0x00) = **バスもアダプタ RX も正常** |

- 結論: 事象時点でアダプタは**電源投入直後と同じ初期状態** (チャネル閉・ビットレート消失) にあった = **CANUSB ファームウェアの内部リセット** (USB VBUS の瞬断・ブラウンアウト、または EMI によるマイコンリセット)。バスオフやエラーパッシブで固まったのではない (`F00`)。kernel から見た USB は切れていない (再列挙なし) ので FTDI 部は生きたまま、CAN マイコン側だけがリセットした形。
- slcand は閉じたチャネルへ `t…` を書き続け、tty 書き込みは成功するので **can0 の送信カウンタは増え続けるがバスには何も出ない**。アダプタは BELL を返すが slcan はそれを捨てる (rx_errors = 1 がその痕跡の可能性)。受信はゼロ。→ EPOS 側は RPDO 途絶 → **0x8250 → クイックストップ** (ユーザ「モータが止まり joy が効かない」と整合)。14:57 の「止まらなかった」はこの型では説明できない (RPDO も止まるはず) → 14:57 は依然別の層 (PC 受信側のみ) か、ユーザ体感の再確認が必要。
- 15:35 型 (kernel `urb -32` + hub port disable) との関係: どちらも **ハブ〜アダプタの電源/信号の瞬断系**として同じ根を持ち得る (15:35 は FTDI 側まで巻き込んだ、19:25 は CAN マイコン側のみ)。ハブの給電・EMI・機械接触 (H4) の識別は未了。
- 補足: EPOS 電源再投入後に heartbeat が見えないのは、0x1017 (2 s) を master が boot 時に SDO で書くため (NVM 既定は 0)。「電源再投入後も受信ゼロ」(§10.4) は heartbeat 不在も寄与しており、アダプタ死の証拠は本節の直接診断の方。
- 対策の含意: (1) `scripts/can_up.sh` の受信ゼロ検知 → service 再起動 (= C/S8/O 再送) は**この型に正しく効く** (今日 4 回とも復帰)。(2) ただし can0 が作り直されるので再 launch は不可避。(3) 恒久策 = 自己リセットしないアダプタ (SocketCAN ネイティブ・絶縁型) か、少なくとも CANUSB を **ノート PC 直結ポート or 外部給電ハブ**へ移す実験 (critic 推奨 2) で「ハブ給電」説を先に潰す。
