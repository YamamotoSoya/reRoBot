# GLIM の CPU 版と GPU 版の差は「ループ閉合が成立するかどうか」— 計算速度ではない (調査中)

**ステータス: 調査中 (本命まで。確定ではない)** — 同一 bag で CPU 既定は長距離閉合 **0 対** (独立 2 run)、GPU は **1215 対**。差の直接の駆動は閉合判定に使う最粗ボクセルの解像度 (CPU 0.5 m 単層 / GPU 1.0〜2.0 m 2 段) と見られるが、**CPU 側で同じ設定を完走させられていない** (2 機で RAM 不足)。前段 odometry の精度自体も CPU 70 m / GPU 36 m と 2 倍違い、閉合の寄与と分離できていない。critic 査読済み (§6 に棄却できなかった仮説)。

- 対象 bag: `bags/raw/2026-10-03_1126_tsukuba` (5149 s = 86 分、往復 2.3 km、同一路を行き帰り)
  - ⚠️ 2026-10-10 現在ローカルには**分割版 `_seg1`〜`_seg4` のみ**。全体 bag は Drive の `cit-share-bags:bags/raw/2026-10-03_1126_tsukuba.tar.zst` (28.5 GB) から復元する
- 関連: GPU 構成の導入と VRAM 落ちは `2026-10-08_glim_gpu_cuda_illegal_address_vram.md` (§6.5 に比較の初出、§7.5 に別 PC 向け実験仕様、§7.6 に 16 GB 機での実施結果)
- 実験ブランチ: `exp/glim-gpu-imu` (headless + IMU 拘束強化。main には入れていない)

## 2. 直接の駆動: 閉合判定に使うボクセルの粗さ

閉合するかは `global_mapping.cpp` が `submaps[i]->voxelmaps.back()` (= **最粗レベル**) で重なりを計算し、`min_implicit_loop_overlap: 0.2` と比較して決める。

| | `submap_voxel_resolution` | `_max` | `submap_voxelmap_levels` | `back()` の解像度 |
|---|---|---|---|---|
| CPU 既定 | 0.5 | なし (= 0.5) | 1 | **0.5 m** |
| GPU 既定 | 0.5 | 1.0 (dmin 5 / dmax 20) | 2 | **1.0〜2.0 m** |

dump の実点群で同じ submap 対の重なりを試算した値 (critic 計測):

| 再訪対 | GPU 相当 2.0 m | GPU 相当 1.0 m | CPU 相当 0.5 m |
|---|---|---|---|
| (0, 620) | 0.434 | 0.282 | 0.148 |
| (142, 532) | 0.343 | 0.231 | 0.128 |
| (139, 532) | 0.236 | 0.143 | 0.047 |

**CPU 設定では 5/5 とも閾値 0.2 に届かず、GPU 設定では 5/5 合格。** 09-20 の CPU 実測 (周回を結ぶ因子 0 本、overlap 0.01〜0.03) とも整合する。

さらに実装差がある: `global_mapping.cpp:244-270` の `insert_submap()` は **GPU 枝が voxelmap に全点を入れ、CPU 枝は `randomsampling_rate` で間引いた点を入れる**。これは config では埋められない。

## 3. 「設定を CPU に移せば同じ」は成立しなかった

| 試み | 機体 | 結果 |
|---|---|---|
| GPU プリセット完全模倣 | 32 GB | bag の **68%** で OOM kill (GLIM RSS 26.7 GB) |
| 閉合判定のボクセルだけ粗く (E1) | 16 GB | bag の **32%** で RAM 92% 到達・watchdog 停止 (RSS 11.3 GB) |

E1 の RSS は既定の約 3 倍 (bag 32% 時点で 11.3 GB 対 3.9 GB)。**「判定を粗くするだけなら記憶消費はほとんど増えない」という当初の見込みは外れ。** voxelmap レベル 2 の保持量倍増だけでは 3 倍を説明しきれず、閉合が立ち始めて因子が増えた分も混ざるが未分離。

**含意**: GPU 版の優位は「GPU で速い」ではなく、**閉合成立に必要な密度/解像度のデータを VRAM に逃がせる**こと。主記憶 32 GB では載らない量が VRAM 8 GB で足りる (1 因子の `source_inliers` 等が GPU 側に置かれるため)。ただし VRAM も無限ではなく、上流既定のままでは 97% 地点で落ちた (別 issue §6)。

## 4. IMU 拘束を強めると全指標が改善した (2026-10-08、1 run)

`config_sensors.json` の IMU 雑音を 1/5 に (= IMU をより信頼する拘束):

```
"imu_acc_noise":  0.05 → 0.01
"imu_gyro_noise": 0.02 → 0.004
```

同時に headless 化 (`config_ros.json` の `extension_modules` から `libstandard_viewer.so` / `librviz_viewer.so` を除外)。

| 指標 | GPU 既定 | GPU + IMU 強化 |
|---|---|---|
| 長距離閉合 | 1215 | **6619** (5.4 倍) |
| traj z 幅 | 36.2 m | **27.7 m** |
| **odom 段 z 幅** | 36.4 m | **32.9 m** |
| 始終点 Δz | 0.59 m | **0.04 m** |
| ピーク RAM / VRAM | — | 15.7 GB / 5793 MiB |

**前段 (odom 段) まで改善している**点が重要。IMU 拘束は推定の前段に効くので、「坂が照合由来の系統誤差で、重力方向を強く信じることが対抗する」という見立てと整合する。閉合が 5 倍に増えたのは、姿勢が正しくなって重なり判定を通る組が増えた結果と考えられる (未検証)。

⚠️ **1 run のみ。** headless 化と IMU 雑音を同時に変えており厳密には未分離 (viewer は受動的で推定に関与しないはずだが未確認)。
⚠️ VRAM は 4728 → 5793 MiB に増えた。headless で空いた分を因子増が食っている。これ以上拘束を増やすと 8 GB に当たる。

## 5. 分割 bag (seg1〜4) は精度では不利 (2026-10-10)

GPU + IMU 強化のまま 4 本を headless 実行した結果:

| 区間 | 収録 | odom z 幅 | traj z 幅 | 長距離閉合 | submap | 所要 |
|---|---|---|---|---|---|---|
| seg1 | 2442 s | 21.5 m | 23.6 m | **0** | 287 | 29 分 |
| seg2 | 1772 s | 14.7 m | **7.7 m** | **924** | 224 | 15 分 |
| seg3 | 455 s | 1.3 m | 2.5 m | **0** | 58 | 3 分 |
| seg4 | 409 s | 3.0 m | 2.6 m | **0** | 71 | 3 分 |

- **閉合がある seg2 だけが最適化で z 幅が縮んだ** (14.7 → 7.7 m)。閉合 0 の seg1/seg3 は**むしろ広がった** (global 段が歪みを増やす既知の傾向と一致)。
- 全体 bag の長距離閉合 6619 対に対し、分割後の合計は **924 対**。往路と復路が別区間に分かれると両者を結ぶ拘束を作れない。
- seg1 の始終点 Δz 18.08 m は異常ではない (区間の終点は出発点ではないため、この指標は全体 bag でのみ意味を持つ)。

**用途の使い分け**: 分割は資源制約の回避と設定比較の高速化には有用 (seg3/seg4 は 3 分)。**地図の品質を上げる方向には働かない。**

## 6. 棄却できなかった代替仮説 (critic)

- **(a) 前段 odometry の実装差が主因** — odom 段の z 幅が CPU 70 m / GPU 36 m と 2 倍違う。これは閉合が立つ前の値なので、閉合の有無では説明できない。GPU odometry は keyframe ベース (`max_num_keyframes: 15`, `OVERLAP`)、CPU は GICP + ivox。**実装か設定かも未分離。**
- **(b) 比較が単発同士** — §1 の各列は 1 run ずつ。実行間ばらつきは実在する (§7)。長距離閉合と z 幅は 2 run で安定していたが、3 run 以上は未取得。
- **(c) `create_between_factors` (CPU true / GPU false) の寄与** — 当初これを主因と考えたが**棄却**。拘束を 1 本外す操作は行きと帰りを結ぶ情報を増やさず、閉合 0 本の CPU 条件では単独で説明できない。ただし CPU の between factor は情報行列に `+1e6·I` がハードコードされており (`global_mapping.cpp:426`)、GICP が退化する DOF (屋外路面の z/pitch) を σ≈1 mm で固定する。**閉合を負かす側として効く可能性は残る** (許容条件であって主因ではない)。
- **(d) CPU の fallback between factor** — `create_matching_cost_factors` 末尾 (L473-481) は `previous_overlap < max(0.25, min_implicit_loop_overlap)` のとき**設定に関係なく** precision 1e6 の between factor を足す。CPU 既定の隣接 overlap は 0.24 (09-20 実測) でこの閾値を下回るため、ほぼ毎回発火していた可能性が高い。GPU は隣接 overlap 0.79〜0.95 で発火しない。**これも「粗ボクセル」の帰結**であって独立要因ではない。

## 7. 評価指標についての注意 (重要)

**再訪 \|Δz\| 中央値 (xy < 1 m かつ Δt > 300 s の組) は単発比較に使えない。** 同一 bag・同一設定の 2 run で **8.92 m → 0.51 m** と 17 倍動いた (標本数も 371 → 183 と半減)。水平 1 m 以内に入る組の抽出が軌跡のわずかなずれで入れ替わるため。

**安定していた指標** (2 run で一致):

| 指標 | CPU 10-03 | CPU 10-08 |
|---|---|---|
| 長距離閉合 | 0 | 0 |
| traj z 幅 | 79.8 m | 77.2 m |
| サブマップ数 | 816 | 817 |

**始点と終点の z 差**は往復 bag でのみ意味を持つが、標本抽出に依存しないので単発でも使える。

評価スクリプトは `bags/glim/2026-10-03_1126_tsukuba_dump/e3_baseline/exp_logs/cmp.py` (別 PC 作成) と、本セッションで使った z 幅/始終点/閉合数版。

5. **64 GB 以上の機体で E1 を完走させる** (別 issue §7.5 の仕様)。CPU + 粗ボクセルで閉合が立つかの決着。
