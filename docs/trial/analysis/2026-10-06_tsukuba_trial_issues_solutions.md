## 2. A 自己位置推定

### A1 傾きのせいで低い帯に市役所の壁が映らない
- **原因 (仮説)**: 帯 (0.3〜1.5 m) を base_link 基準の相対高さで切っているため、機体や地面が傾くと、遠くの壁ほど帯の外に出る。1° の傾きで 30 m 先は 0.52 m ずれる。既知の前下がり (約 0.85°、`scan-ground-ghost` メモ) と坂だけでも、この量のずれは起こりうる
- **対策**
  - 短期: AMCL の帯上限を 3.0 m にする (`loc_0.3-3.0`。10-04 の P1 構成ですでに切り替えられる)。帯を上に広げれば、傾いても壁の上部が帯に残る
  - 中期: `/scan_all` を作る前に、IMU (EKF) の roll/pitch で点群を水平に戻す。坂の上での相対高さ問題 (10-03 の改善点) もこれで一部解消する
  - 根本: P3 (地面除去) / P4 (3D 地図での自己位置推定)。10-03 の計画どおり

### A2 スタート付近は植木が建物より手前にある
- **対策**
  - 帯上限 3 m: 植木 (〜2 m) の上から建物が見える。A1 と同じ切り替えで効く
  - 初期姿勢を固定値にする: スタート地点は毎回同じなので、`initial_pose` を launch 引数で与える (RViz の 2D Pose Estimate を手で置く誤差がなくなる)
  - 林原研方式: 一度建物の近くでマッチングさせてからスタート地点へ移動する。A5 の停止中更新と組み合わせる
  - 位置推定用地図から植え込みを消す (A3 の「重み 0」案)

### A3 地形でマッチングの強さを変えたい (重み付き地図)
- 事実: AMCL の likelihood_field は**セル単位の重みを持てない** (地図は占有か空きの 2 値。z_hit などのパラメータは地図全体で 1 つ)
- **案** (簡単な順)
  1. 位置推定用地図 (`loc_*`) で、信頼できない領域 (植え込み・草・季節で変わるもの) を塗りつぶす = 重み 0。GIMP の手作業でできる。帯ごとに地図を分けた今の構成なら、経路計画用の地図には影響しない
  2. 区間ごとにパラメータを切り替える: `waypoint_runner` が区間を切り替えるときに `ros2 param set /amcl z_hit ...` を呼ぶ。広場と通路で `laser_sigma_hit` や `max_beams` を変える
  3. 地図そのものに重みを持たせる: 自作のセンサモデルが必要 (emcl2 のフォークなど)。費用対効果が低いので後回し

### A4 emcl2 の導入
- 利点: 膨張リセット (見失ったら粒子を広げて復帰する)、信頼度 α を出す (B3・C の停止判断にも使える)。過去チームの 2548 (R-Fans16 + GLIM + emcl2) と 2563 は、我々とほぼ同じ構成
- 確認事項: `emcl2_ros2` の Jazzy 対応 (**未確認**)、map_server・`/scan_all`・`initialpose` の入出力が AMCL と同じか
- 評価: `tools/amcl_compare` と同じやり方 (同じ bag の反復再生 + 総当たり照合)。単発の再生では判定しない (`amcl-replay-pitfalls`)

### A5 停止中に AMCL が推定しない
- **原因 (設定から確実)**: `update_min_d: 0.25` / `update_min_a: 0.2` (`nav2_params.yaml:60`)。動かない限りフィルタを更新しない仕様
- 止めたまま毎周期更新すると、同じスキャンでリサンプリングが繰り返され、粒子が一点に過収束する。そのため値を小さくして常時更新させるのは悪手
- **対策**: AMCL の `request_nomotion_update` サービス (std_srvs/Empty) を、必要な時だけ呼ぶ
  - スタート前: 初期姿勢を与えた後に数回呼ぶ (またはその場で少し旋回させる)
  - `waypoint_runner` の停止点で待機に入ったときに数回呼ぶ → 再開前に姿勢を締める
  - 実装: `waypoint_runner.py` にサービスクライアントを 1 つ足すだけ

### A6 林原研方式 (2D 直接・20 m・slam_toolbox で 10 m)
- 示唆: 遠方を使わず、10〜20 m の近傍構造で照合している。我々の `/scan` では 12〜25 m の終点の約 6 割が地面だった (`scan-ground-ghost` メモ) ので、遠方を切るのは理にかなう
- **対策**: `laser_max_range` 30 → 15 / 20 m を `amcl_compare` で比較する (帯上限 1.5 / 3.0 との組み合わせ)
- 「3D を挟まない」点について: 我々は GLIM でループを閉じた地図を持っているので、ここは真似しない (地図の歪みは 3D 経由の方が小さい)

## 3. B 経路計画・走行の挙動

### B1 狭い場所で膨張に挟まれる / 道が細い
- 現状: `robot_radius: 0.35` (外接円) + `inflation_radius: 0.55` + `cost_scaling_factor: 3.0`。外接円は横幅 0.35 m の車体を直径 0.70 m の円として扱うので、細い道では過大になる
- **対策**
  1. `robot_radius` を `footprint` (0.50 × 0.35 の多角形) に置き換える (local・global の両方)
  2. `cost_scaling_factor` を 3 → 5〜8 に上げて、膨張のコストを壁の近くで急に落とす。道の真ん中が「通れる谷」として残る
  3. 細い区間だけ速度を落とす: keepout と同じ仕組みの SpeedFilter で、地図上の区間に速度上限をかける

### B2 狭い場所で「待つ」動作がない
- 現状の BT は計画に失敗すると Spin / BackUp に入る。狭い場所や人の前では危険
- **対策**
  - 復帰動作 (recovery) を `Wait` を中心にした BT に差し替える (Spin・BackUp は外すか最後の手段に)
  - Nav2 の collision_monitor で、前方の多角形に点が入ったら停止 / 減速 (`/scan` か点群を直接読む)。経路計画とは別の安全層として働く
  - 過去事例: 2408 (待機中は recovery を無効化)、2540 (速度フィルタの優先順位)

### B3 一時停止 (白線・横断歩道) と、その前でぐるぐる回る問題
- 現状: 10-04 に停止点つきの `waypoint_runner` を実装済み (停止点でゴールが完了 → キーで再開)。ゴールが完了してから待つので、ぐるぐる回る問題は構造上起きない
- 残る課題は**停止位置の精度**
  - 停止点だけ goal checker の許容を締める (`xy_goal_tolerance`)。Nav2 の goal checker は全ゴール共通なので、停止点用に別の goal checker プラグインを登録し、ゴールごとに選ぶ方式が要る
  - 止まる位置の誤差 = 自己位置誤差 + 許容値。A5 (停止前の nomotion update) とセットで効く
  - 白線を直接検出する方法は選択課題レベルの作業量なので、今季は地図座標で止める

### B4 途中から復帰できる waypoint 設計
- 現状: `--start N` で途中から再開できる (番号は人が選ぶ)
- **対策**
  - `--start auto`: 現在の AMCL 姿勢から、最も近い「前方の」waypoint を自動で選ぶ
  - コース設計: 復帰しやすい場所 (建物が見えて自己位置が安定する場所) に停止点を置き、そこを再開ポイントにする

### B5 keepout のズレで草地に入る
- 原因の候補: (a) AMCL の横方向誤差、(b) keepout 地図そのものの描画ずれ。どちらが効いているかは未確認
- **切り分け**: 走行 bag の AMCL 軌跡を GLIM 軌跡 (正解代わり) と比べる。(a) が主因なら A の対策で直る。(b) なら地図の手直しで直る
- 当面は、草地との境界の keepout を 0.2〜0.3 m 太らせる (B1 の細道と競合するので、場所を選んで)

### B6 waypoint editor の位置ずれ
- 疑う順: 地図 yaml の `origin` / `resolution` の読み違い → 画像の y 軸反転 → nav2 地図と loc 地図の取り違え (原点が違う可能性)
- 確認: 既知の座標 (地図原点・角) に点を置き、`--check` の出力と RViz の表示を比べる。**要調査**

### B7 障害物 (足元の草・ススキ・坂の見えない壁)
- 10-03 の計画 P0 → P2 → P3 のとおり。ススキは人に当たる高さなので「避ける対象」として扱うのが正しい。避けられない細道では B2 の「待つ・減速」に落とす

## 4. C 安全・運用

### C1 コントローラ → 自律の切り替え (cmd_vel の干渉)
- 現状: joy (`teleop_twist_joy`) と Nav2 が、どちらも `/robot_speed_cmd` に直接 publish している。LB を押している間は 2 つの指令が交互に届く
- **対策: twist_mux を挟む**
  ```
  joy  → /cmd_vel_joy ─┐ 優先度 高 (LB を押している間だけ出る = 人がいつでも割り込める)
  Nav2 → /cmd_vel_nav ─┼→ twist_mux → /robot_speed_cmd → epos4_controller
  (lock) /pause (Bool) ─┘ 一時停止ボタン: true の間は全ての指令を止める
  ```
  - LB を離せば 0.5 s 程度で Nav2 の指令に戻る (twist_mux の timeout)
  - `epos4_controller` の `cmd_timeout_s` (0.5 s) はそのまま有効
  - Nav2 は手動介入中も動き続けるため、長い介入の後は progress checker でゴールが失敗しうる。`waypoint_runner` は失敗を待機として扱うので、再開キーで続けられる

### C2 非常停止後に再起動が要る
- 現状: 非常停止はモータ電源 (RSD → DSR → EPOS +Vcc) だけを切り、EPOS のロジック電源と CAN は生きている (09-19 issue の harness v2 図)。EPOS は低電圧フォルトになると推定され (**実機で未確認**)、今は自動で復帰しない
- **対策**
  - `epos4_controller` に「再有効化」を追加する: 各モータの `~/recover` (canopen_402_driver のサービス、フォルトリセット) → `enable` → `cyclic_velocity_mode`。脱力モードからの復帰 (`/robot_free_mode` false) と同じ逐次呼び出しの経路を流用できる
  - 起動の契機は**人の操作** (joy の Start ボタン → `/robot_reenable`)。非常停止を解除しただけで勝手に動き出さないようにする (安全面の要件。2009 チームも解除後の動き出しを加速度制限している)
  - 再有効化の前に目標値とランプを 0 にリセットする (前の指令が残って急発進しないように)
- **最初にやること**: 非常停止 → 解除のときの statusword とエラーコードを `/diagnostics` で記録し、どのフォルトになるかを確定させる

### C3 USB が抜けても止まるように
どの USB を想定するかで答えが変わる。現状を USB ごとに並べる:

| 抜けたもの | 今どうなるか | 対策 |
|---|---|---|
| CANUSB | 監視ループが can0 の消滅を検知して目標を 0 に固定。EPOS 側は 0x8250 (RPDO timeout) で停止 (09-19 の実例あり) | 済み。加えて EPOS に heartbeat consumer (0x1016) を設定すると、PC 側のハングでも 0x6007 = quick stop が確実に働く |
| ゲームパッド | joy が止まる → `cmd_timeout_s` で 0 へ | 済み (C1 の twist_mux を入れた後も timeout で同じ挙動) |
| **R-Fans (Ether-USB) / UTM** | **`/scan` が途絶えても Nav2 は古い costmap のまま走り続ける可能性が高い** | observation source に `expected_update_rate` を設定 → costmap が「古い」と判定し controller が止まる。collision_monitor (B2) も入力が途絶えると止まる設定にできる |
| BNO086 | EKF は車輪 odom だけで走り続ける | 走行は継続してよい。`/diagnostics` で警告するだけ |

- 「USB が抜けても止まる」の本命は**センサ系**だと思われる (CAN 系はすでに止まる)。物理面では、2403 (USB の緩みを自動監視)・2459 (振動でケーブルが抜けた → ロック付きコネクタ) の事例がある

### C4 起動コマンド・bag 記録コマンドが長い
- 起動: `tsukuba.launch.py` を 1 本作る。bringup (3D + IMU + EKF) + `rfans_scan` (allpoints) + nav2 を、`map_dir` と `H` (帯上限) の 2 引数だけで起動する。中身は今手で打っている 3 本の include なので、素の `ros2 launch` のまま短くなる
- bag 記録: topic 一覧を launch 内の `ExecuteProcess` にまとめる (`record:=true slug:=tukuba_yakusho`)。記録の前に ws を source するという罠 (`bag-record-needs-ws-sourced`) も同時に解消する

### C5 小物
- `/scan_all` の常時表示: `nav2.rviz` に LaserScan の Display を 1 つ追加する
- joy の加減速: `epos4_controller` のランプは Nav2 と共有しているので、joy 側だけ緩めたいなら `teleop_twist_joy` の後段 (twist_mux の手前) に velocity_smoother を入れる。全体で緩めてよいなら、ランプのパラメータを変えるだけ
- 遠隔操作: CRD の GNOME 二重セッション問題 (設定が 3 秒で戻る) → CRD の仮想セッションだけ Xfce にする (`~/.chrome-remote-desktop-session` に `exec xfce4-session`) か、Parsec に移行する。Parsec は物理セッションを映すので二重セッションの問題は起きない

## 5. D ハードウェア
