# 第6章 事例集 — reRoBot で実際に起きた融合バグ

理論は前章まで。この章は原則を破るとどう壊れるかの実録である。
特筆すべきは事例A〜Cが**すべて 2026-08-11 の初回実機テスト 1 回で同時に
発覚した**こと — 融合システムの初回起動は、上流に潜んでいた欠陥の
一斉検出器として働く。

| 事例 | 一言でいうと | 破った原則 | 状態 |
|---|---|---|---|
| [A](#事例a) | /odom の twist が常時 0 で EKF の位置が進まない | フィールドの存在 ≠ 値の有効性 ([第3章](03_feeding_the_filter.md) §3.2) | ✅ 修正済 (2026-08-11) |
| [B](#事例b) | IMU の向き判定が 2 転 3 転 | 検証は目視でなくデータ照合 ([第5章](05_rerobot_architecture.md) §5.3) | ✅ 確定 (2026-08-11) |
| [C](#事例c) | teleop の距離表示が 51 m (実際は ~10 m) | ノードは params ファイル込みで起動する | ✅ 修正済 (2026-08-11) |
| [D](#事例d) | 360° 旋回で融合出力が生 odom より悪い | 質の悪い情報源は混ぜると悪化する ([第1章](01_why_fusion.md) §1.3) | ⚠️ 未解決 |
| [E](#事例e) | エンコーダ較正 4 倍ズレ、実車が指令の 1/4 速 | 入力の較正は融合の前提 ([第1章](01_why_fusion.md) §1.1) | ✅ 修正済 (2026-07-29) |
| [F](#事例f) | stamp=0 で左右輪ペアリングが到着順に退化 | stamp は計測時刻 (タイムスタンプ読本) | ⚠️ 潜在欠陥として残存 |

## 事例A

**/odom の twist が常時 0 — ロボットが 20 m 走っても EKF は (0,0) のまま**

- 一次資料: `docs/claude/PROJECT_STATE.md` タイムライン 08-11 (2)、bag `ekf_test`
- 対象コード: `ros2_ws_main/src/app/epos4_controller/src/epos4_odometry.cpp` (`syncCallback()`)

### 症状

初回実機テストで `/odometry/filtered` が終始ほぼ (0,0)。bag を解析すると、
`/odom` の pose は 20 m 分きれいに動いているのに、**twist は全区間で
0.05 m/s を超えたことが一度もなかった**。

### 機構

三題噺である:

1. ros2_canopen ドライバの `joint_states.velocity` は、速度オブジェクト
   0x606C が bus.yml で PDO マップされていないため**常に 0**。ただし配列
   としては常に存在する (非空)。
2. 旧 epos4_odometry は「velocity 配列が非空なら位置差分より velocity を
   優先」というロジックだったため、twist は静かに 0 のまま publish され続けた。
3. `ekf.yaml` の `odom0_config` は**速度しか採用しない** ([第4章](04_robot_localization.md) §4.1)。
   pose を見る SLAM (slam_toolbox) では何ヶ月も無症状だった欠陥が、
   twist しか見ない EKF に繋いだ日に初めて発症した。

「静かに」が肝で、`empty()` チェックでは検出不能 (空ではない)、
値のゼロチェックでも検出しにくい (静止中は正当に 0)。**実走 bag で
pose の変化量と twist の積分を突き合わせて初めて矛盾が見えた**。

### 修正

velocity フィールドへの依存を完全に捨て、位置差分から twist を導出する
(`epos4_odometry.cpp:151-158`、コード解説は [第3章](03_feeding_the_filter.md) §3.2 (2))。

### 教訓

- フィールドが存在することと有効な値が入っていることは別 — 新しい上流と
  繋ぐときはフィールドごとに実データで値域を確認する ([第7章](07_verification.md) 検収 №4)
- 消費者が変わると発症する欠陥がある。「今まで動いていた」は
  「全フィールドが正しい」を意味しない

## 事例B

**IMU の向き判定が 2 転 3 転 — 目視 vs データ照合**

- 一次資料: `docs/claude/PROJECT_STATE.md` §2 (BNO086 の項)・§4・タイムライン 08-11 (2)(3)
- 対象コード: `ros2_ws_main/src/bringup/rerobot_bringup/urdf/rerobot.urdf:105-132` (imu_joint)

### 症状

URDF に書く IMU の取付向き (rpy) の判定が短期間に 3 回覆った:
08-10 のデータ照合では「正立」→ 08-11 朝の RViz 目視では「裏返しに見える」
→ 同日の実走 bag 解析で「正立」に再確定。裏返し版 URDF で EKF を回すと、
**EKF の yaw が車輪 odom の yaw の鏡像** (-79° vs +74°) になった。

### 機構

2 つの独立した罠が重なった:

1. **可視化の罠**: 目視判定に使った `imu_check.rviz` に
   `fixed_frame_orientation: true` という表示設定が入っており、姿勢の
   見え方が実データと異なっていた。「RViz で見たまま」は設定 1 個で嘘をつく。
2. **鏡像の伝播**: URDF の imu_joint が実際と逆だと、EKF は TF で軸変換した
   時点で yaw の符号が反転した「測定」を受け取る ([第3章](03_feeding_the_filter.md) §3.3 の 1)。
   IMU 自体は正しくても、**取付定義の誤りは観測の誤りとして忠実に融合される**。
   旋回方向が逆の推定は、Nav2 に渡れば即座に制御の暴走になる。

### 修正

目視を捨て、実走 bag からの 3 系統のデータ照合で rpy = (0, 0, +90°) を確定
([第5章](05_rerobot_architecture.md) §5.3 に 3 証拠の詳細)。
あわせて「URDF の imu_link は基板の見た目ではなく /imu/data のデータ座標系を
表す」という原則を明文化した。

### 教訓

- センサの取付向きの検証は、静止重力 (accel z の符号) と
  旋回相関 (gyro ⇔ 車輪 yaw rate の符号) のデータ照合を正とする
- 鏡像バグの症状は特徴的:「片方の yaw がもう片方の -1 倍」を見たら
  まず取付定義を疑う ([第7章](07_verification.md) 逆引き表)

## 事例C

**teleop の距離表示が 51 m — params ファイルを渡し忘れて起動**

- 一次資料: `docs/claude/PROJECT_STATE.md` タイムライン 08-11 (2)

### 症状

初回テスト中、teleop の走行距離表示が 51 m を示した。実際の走行は 10 m 強。

### 機構

teleop ノードを `--params-file` なしで起動したため、`gear_ratio` が
宣言時の既定値 1.0 のまま動いた (正しくは 5.0、`params.yaml:26`)。
距離計算 `Δposition / gear_ratio × 半径` の分母が 1/5 になり、
表示が 5 倍に膨れた (51 m ÷ 5 ≈ 実際の ~10 m と整合)。

EKF 本体の問題ではないが、テスト計画の中で「基準として信じるはずの表示」が
狂っていたため、他の 2 バグ (A, B) の切り分けを一時混乱させた。
**検証に使う物差し自体の較正確認**が先、という教科書的な失敗である。

### 修正

params ファイル付きの正しい起動コマンドで再起動
(CLAUDE.md の手動起動手順に `--params-file` が明記されているとおり)。

### 教訓

- 車体パラメータは複数ノードに重複配布されている (`/params-sync` skill で検査可)。
  「どのノードがどの params で起動したか」は `ros2 param get` で必ず確認できる
- 検証セッションの最初に、物差し (距離表示・スケール) を既知の移動量で較正する

## 事例D

**360° 旋回の残差: filtered +3.9° vs 生 odom 0.1° — 融合の方が悪い**

- 一次資料: `docs/claude/PROJECT_STATE.md` タイムライン 08-11 (3)・§10 (次の作業)
- 状態: ⚠️ **未解決** (原因は仮説段階、対策候補のみ列挙)

### 症状

修正後の再テスト (bag `ekf_test2`)。その場 360° 旋回して元の向きに戻したとき、
生の車輪 odom の yaw 残差は 0.1° とほぼ完璧だったのに対し、
**EKF 出力 `/odometry/filtered` の残差は +3.9°** だった。
静止ドリフト・直進では filtered は良好 ([第5章](05_rerobot_architecture.md) §5.4) で、
旋回だけ融合が足を引っ張っている。

### 機構 (仮説)

`imu0_config` は yaw (姿勢) を採用しており ([第4章](04_robot_localization.md) §4.1)、
BNO086 の yaw は磁力計込みの融合値である。`imu0_relative: true` は
起動時基準への相対化 (静的な磁北依存の除去) はするが、
**旋回中に磁場環境が変わることによる動的な yaw の揺れは除去できない**
([第4章](04_robot_localization.md) §4.4)。車体のモータ・フレームや周囲の鉄が作る磁場は
車体の向きによって変わるため、旋回はまさに磁気外乱が最も動く操作である。
σ² 的には IMU の yaw はチップの自己申告精度で報告される
([第3章](03_feeding_the_filter.md) §3.4) が、磁気外乱はチップの自己申告に
正しく乗らないことがある — 「自信満々の間違った測定」は重み付き平均を汚す。

### 修正 (候補、未適用)

1. `imu0_config` の yaw を false にし、**yaw rate のみ融合**する
   (ジャイロは磁気と無関係)。yaw は EKF が yaw rate を積分して持つ
2. ドライバを `use_game_rotation_vector: true` に切り替え、
   磁力計を使わない姿勢 (`bno086.yaml:33-42` に選択根拠の記述) にする

どちらも「磁北という汚れうる情報源を切る」方向。現状維持なのは、
Nav2 実走行 ([第5章](05_rerobot_architecture.md) §5.4 の未実施項目) での実害評価が先だから。

### 教訓

- 融合は情報源の質を超えられない。悪い情報源は「入れて共分散で薄める」より
  「入れない」が正しいことがある
- 検証は運動の種類別に行う (静止・直進・旋回)。旋回だけ悪い、のような
  **選択的な劣化がセンサ固有の弱点 (磁気・滑り) を指差してくれる**

## 事例E

**エンコーダ較正 4 倍ズレ — 実車が指令の 1/4 速で走っていた**

- 一次資料: `docs/issue/2026-07-07_wheel_odometry_encoder_scaling_4x.md` (調査記録の全容はこちら)
- 対象: `bus.yml` (`scale_pos_from_dev`) + `params.yaml` (`gear_ratio`)

### 症状

実車の走行速度が指令値の約 1/4。オドメトリ距離と実測距離も一致しない。

### 機構

bus.yml のエンコーダ分解能が実機と 4 倍ズレていた (2π/4096 として設定、
実機は 256 pulses × 4 逓倍 = 1024)。さらにこのズレを `gear_ratio: 1.25`
(物理的には 5.0) が**偶然相殺する形で「較正」されていた**ため、
オドメトリ距離だけ見ると辻褄が合い、速度が 1/4 である事実が隠れていた。
2 つの誤りが打ち消し合う較正は、どちらか片方を直した瞬間に 4 倍狂う地雷になる。

### 修正

2026-07-29 に bus.yml (2π/1024) と gear_ratio (5.0) を**2 点同時修正**。
経緯・検証は issue ファイルに詳しい。

### 教訓

- 融合 (2026-08-11) の 2 週間前にこの較正が済んでいたことは幸運だった。
  未較正のまま EKF を入れていたら、「vx が 1/4 の /odom」と「正しい IMU」の
  矛盾を共分散の重みで中途半端に折衷した、原因追跡困難な推定になっていた
- **入力センサの較正は融合の前提** ([第1章](01_why_fusion.md) §1.3)。
  融合を入れる前に、各センサを単体で実測に対して検収する

## 事例F

**stamp=0 で左右輪ペアリングが到着順に退化 (要約)**

- 一次資料: `docs/issue/2026-08-01_odometry_stop_wobble_zero_stamp_pairing.md`
- 本解剖: [タイムスタンプ読本 第6章 事例C](../timestamp/06_case_studies.md) (正典はあちら)

ros2_canopen の `joint_states` は `header.stamp` が常に 0 のため、
epos4_odometry の ApproximateTime 同期が実質「到着順ペアリング」に退化して
いる。現状は実害の観測なし (だからこそ潜在) だが、`/odom` は EKF の入力で
あり、左右の取り違えは d_theta ([第3章](03_feeding_the_filter.md) §3.2) の誤差として
融合に流れ込む。EKF 入力の品質は上流の stamp 品質に上限を握られている、
という接続だけ本書から押さえておく。

## 章のまとめ — 事例を貫く一本の線

```
事故の共通構造
├── 「入力は正しい」という無根拠な信頼 (A: velocity, B: RViz 表示, C: 距離表示)
│   └── 融合器は疑わないので、疑うのは人間の仕事
├── 消費者が変わると発症する休眠欠陥 (A: SLAM→EKF, E: 相殺較正)
│   └── 「今まで動いていた」は検収の代わりにならない
├── 検証の物差し自体の較正 (B: rviz 設定, C: gear_ratio, E: 相殺)
└── 情報源の質は融合で救えない (D: 磁北, E: 未較正なら同型の事故に)
```

→ [第7章 検証とチェックリスト](07_verification.md) — この共通構造を潰すための
定型手順に落とす。
