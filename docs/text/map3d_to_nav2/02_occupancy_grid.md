# 第2章 占有格子の正体 — 画像 + yaml がなぜ地図になるのか

第 1 章の入力①、`/map` の中身を解剖する。占有格子は「ただのグレースケール画像」と
「6 行の yaml」でできている。単純だが、ピクセル値の解釈が 2 段階の翻訳を経ること、
そして origin という 1 行が座標系の接続を全部担っていることは知らないと事故になる。

## 2.1 地図 = 画像 + メタデータ

map_server に渡す「地図」は 2 ファイルの組である:

```
地図一式
├── 画像ファイル (.pgm / .png)
│     グレースケール画像。1 ピクセル = 1 セル。
│     慣習: 黒 (0) = 占有、白 (254/255) = 自由、灰 (205) = 未知
└── yaml ファイル
      image:           画像ファイル名 (相対パス)
      resolution:      1 ピクセルの辺長 [m] (reRoBot は 0.05)
      origin:          [x, y, yaw] — 画像の「左下」ピクセルの map 座標
      occupied_thresh: これより高い占有確率 → 占有 (100)
      free_thresh:     これより低い占有確率 → 自由 (0)
      negate:          白黒の意味を反転するか (通常 0)
      mode:            trinary (既定) / scale / raw
```

実例 — 今回 GLIM 地図から生成した `maps/glim/2026-08-14_N12/nav2/my_map.yaml`:

```yaml
image: my_map.png
resolution: 0.05
origin: [-51.2, -51.2, 0.0]
occupied_thresh: 0.5
free_thresh: 0.2
negate: 0
```

## 2.2 ピクセル値の 2 段翻訳

map_server は画像を読むとき、ピクセル値をそのまま使わない。2 段階の翻訳を経て
OccupancyGrid の値 {0, 100, -1} になる:

```
段階 1: ピクセル値 → 占有確率 p
    p = (255 - ピクセル値) / 255       (negate: 0 のとき)
    黒 (0)   → p = 1.0  「確実に占有」
    白 (255) → p = 0.0  「確実に自由」
    灰 (205) → p = 0.196「たぶん自由だが確信なし」

段階 2: 占有確率 p → セル値 (mode: trinary)
    p > occupied_thresh → 100 (占有)
    p < free_thresh     →   0 (自由)
    それ以外            →  -1 (未知)
```

この 2 段目が重要である。**閾値の間に落ちた中間グレーは「未知 (-1)」になる**。
slam_toolbox の保存地図で灰 205 が未知を意味するのはこの仕組み
(p=0.196 が free_thresh=0.196 と occupied_thresh=0.65 の間に落ちる) であり、
「灰色という特別な色」がある訳ではない。

第 3 章で見る pointcloud_to_2dmap はこの仕組みを逆手に取り、点数の中間帯を
グレー階調で出すことで「確信の持てないセル」を未知に落としている。

## 2.3 origin — 座標系の接続点

yaml の origin は「画像の左下隅ピクセルの中心が、map 座標系のどこにあるか」を定義する。
画像は行 0 が上端なので、上下の対応に注意:

```
map 座標系 (y 上向き)               画像 (行番号 下向き)
        ▲ y                          row 0  ┌──────────┐ ← 画像の上端
        │                                   │          │
        │   地図領域                        │          │
        │                            row H-1└──────────┘ ← ここの左端セルが
        └────────▶ x                                        origin [x, y]
   origin = 左下
```

セル (col, row) と map 座標 (x, y) の変換:

```
x = origin_x + (col + 0.5) × resolution
y = origin_y + (H - 1 - row + 0.5) × resolution
```

**origin が正しいから、3D 地図由来の座標がそのまま 2D 地図で通じる**。
pointcloud_to_2dmap は world (0,0) を画像中心に置き、origin に
`[-resolution×W/2, -resolution×H/2, 0]` を書き出す
(`tools/pointcloud_to_2dmap/src/pointcloud_to_2dmap.cpp:116`)。
2048 px @ 0.05 m なら origin = [-51.2, -51.2, 0] — §2.1 の実例と一致する。
これにより「GLIM 地図の (10, 5) 地点」は 2D 地図でも (10, 5) であり、
RViz で 3D 点群と 2D 地図を重ねてもズレない。

⚠️ 逆に言うと、**origin を書き間違えると地図全体が平行移動する**。自己位置も
ゴールも全部ずれるが、地図単体を見ても異常に気づけない (第 7 章の逆引き表参照)。

## 2.4 「未知」は誰のために要るのか

自由 (0) と未知 (-1) の区別は、消費者によって重みが違う:

```
未知セルの扱い
├── AMCL (自己位置) ....... ほぼ無関心。照合に使うのは占有セルだけ (第4章 §4.3)
├── global costmap ........ track_unknown_space: true なら未知に高コスト
│     (reRoBot の設定: ros2_ws_main/src/bringup/rerobot_bringup/config/nav2_params.yaml)
│     → planner が未知領域を避けて経路を引く
└── 運用者 (人間) ......... 「そこは地図に無い」が見える安全情報
```

pointcloud_to_2dmap の制約「点が無い場所は全部白 (自由)」(第 3 章 §3.3) が
実害を持つのは主に costmap/planner に対してである。未探索の脇道にも経路を
引けてしまう — 屋内の閉じた環境では壁が全周を囲むので実害は小さいが、
屋外の開けた環境では keepout マスク (進入禁止帯) で補う運用が現実解になる。
