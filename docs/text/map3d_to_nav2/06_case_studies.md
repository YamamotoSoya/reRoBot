## 事例A

**R-Fans の 0° リングを slam_toolbox に食わせたら、壁がシャープに閉じた 2D 地図が出た**

- 一次資料: `docs/claude/PROJECT_STATE.md` タイムライン 08-12 (3)、成果物 `maps/rfans2d_slam.png`
- 元々の目的: GLIM 3D 地図の水平ドリフトの原因切り分け (R-Fans データ自体の無罪証明)

### 症状 (結果)

GLIM では水平に塗れていた同じ bag から、R-Fans の水平リング (laserid 7 = 仰角 −1°) を
LaserScan 化して slam_toolbox に通したところ、占有 9,250 セルの綺麗な 2D 地図が出た。

### 機構

これは第 3 章 §3.5 の「経路B (bag から 2D SLAM)」の実演であり、成立の鍵は 2 つ:

1. **車輪 odom prior**: slam_toolbox はスキャンマッチングの初期値に車輪オドメトリを
   使う。長い廊下 (縮退環境) で進行方向を拘束できたのはこれ。GLIM が同じ環境で
   塗れたのは車輪 odom を使わないから — 犯人はデータではなく prior の有無だった
2. **レイキャストが本物**: SLAM 中は「センサからビーム先端まで」の視線が分かるので、
   自由/未知/占有の 3 値が正しく塗り分けられる (完成点群からの変換では失われる情報)

### 教訓

- 経路B は「GLIM を使わない 2D 地図作成」の実証済み手段として温存する価値がある。
  特に**屋内は 2D 地図の方が品質が高い**現状では、9 号館運用の本命であり続ける
- ただし出てくる地図の座標系は slam_toolbox の初期姿勢基準で、GLIM 地図とは origin が
  一致しない。3D 地図と重ねる用途には使えない

## 事例B

**pointcloud_to_2dmap が Jazzy でビルドエラー — `boost::make_shared` が未宣言**

- 一次資料: `docs/features/2026-08-17_glim_map_to_nav2.md` §2.2、`tools/README.md`
- 対象コード: `tools/pointcloud_to_2dmap/src/pointcloud_to_2dmap.cpp` (`main()` 内)

### 症状

glim コンテナ (Ubuntu 24.04 / Boost 1.83) で `make` すると
`error: 'make_shared' is not a member of 'boost'`。上流リポジトリでは Issue にも
なっていない = 古い環境では誰も踏まない。

### 機構

ソースは `boost::make_shared` を使うのに `<boost/make_shared.hpp>` を include して
いない。古い Boost/PCL では**別のヘッダが連鎖 include で偶然持ち込んでいた**ため通って
いた。Boost 1.83 / PCL 1.14 でヘッダ整理が進み、偶然の供給が絶たれて未宣言になった。
「自分の書いた include だけで自分の使う名前が揃う」原則 (include what you use) を
破ったコードは、環境更新でこの形で発火する。

### 修正

ソースを触らず、コンパイラの強制 include で解決した:

```bash
cmake .. -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_FLAGS='-include boost/make_shared.hpp'
```

ソースにパッチする案を却下したのは submodule の運用上の理由 — 直接編集すると
gitlink が「上流に存在しない commit」を指すか dirty のまま残り、
`git submodule update` で再現できないリポジトリになる。ビルドフラグなら
上流 pristine のまま手順だけで再現できる (`tools/README.md` に恒久記録)。

### 教訓

- ベンダ/外部コードの「ビルドが通らない」は、まず**ソースを触らない解決** (フラグ・
  環境変数・ラッパ) を探す。submodule の pristine 性は再現性の担保
- 「昔は通った」系のビルドエラーは include の偶然依存をまず疑う

## 事例C

**GLIM 地図の床は z=+0.636 にあった — 地図の原点はどこか**

- 一次資料: `docs/features/2026-08-17_glim_map_to_nav2.md` §4.1 (実測コマンド)
- 対象データ: `bags/9goukan/2d3d_imu/offline/glim/exp_2026-08-14/N12/N12_dense_map.ply`

### 症状

高さスライスの帯を決めるため床 z を実測したら、床は z=0 でも z=−0.75 (センサ高さの
逆符号) でもなく **z=+0.636** にあった。素朴な想定 (「地図の z=0 は床のはず」) の
どちらとも違う。

### 機構

GLIM (LIO) の world 原点は「マッピング開始時のセンサ位置」で、z 軸だけが重力に
アラインされる。センサは床から ~0.75 m (rfans) / 0.64 m (IMU) の高さにあるので、
素朴には床は z=−0.6〜−0.75 に出るはずだが、実測は **+0.636** と符号が逆だった。
初期化がどのセンサ基準か・T_lidar_imu の並進がどの向きに効くかという GLIM 内部の
初期化系列に依存しており、**正確な機構は未追跡** (追うなら glim の odometry 初期化と
dump の T_world_origin 系列)。ここで重要なのは機構の詳細ではなく、
「床がどこか」は**設定から演繹するより実測が速くて確実**という運用判断である。
5 cm ビンの z ヒストグラム最頻値なら屋内地図で 1 コマンドで出る (第 3 章 §3.3)。

### 修正 (運用)

変換手順に「床 z の実測」を必須ステップとして組み込んだ (第 7 章のチェックリスト)。
帯は常に「実測床 z + 0.3〜1.5」で指定し、地図が変わるたびに測り直す。

### 教訓

- **「z=0 は床」を仮定しない**。3D SLAM の原点は開始時のセンサ位置で、
  しかもどのセンサ (IMU/LiDAR) 基準かは実装依存
- 演繹 (URDF から計算) と実測が食い違ったら実測を採る — IMU 取付向き事件
  ([EKF センサ融合読本](../ekf_fusion/00_index.md) 事例B) と同じ教訓の再演
