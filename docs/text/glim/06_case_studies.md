## 事例A

**水平ドリフト — 床は完璧、壁は数 m の帯**

- 一次資料: `docs/issue/2026-08-12_glim_horizontal_drift.md` (112 行 +
  `docs/issue/img/2026-08-12_glim_drift/` PNG 5 枚)
- 対象: GLIM 1.2.2 LIO 構成、9 号館 235 s bag (`glim_rosbag` オフライン再現)

### 症状

3D 地図の**垂直方向は健全** (床の傾き 0.1°) なのに、**水平方向で壁が数 m の帯に塗れる**。
破綻 (発散) ではなく、じわじわ流れる moderate なドリフト。

### 機構 — 4 段の切り分けで仮説が 2 回覆った

診断の過程そのものが教材なので、時系列で追う:

```
切り分けの 4 段 (各段が 1 つの仮説を殺す)
├── 段1: 入力データが悪い?
│   ├── 実験: /sdk_could の水平リング (仰角 -1°) を LaserScan 化し slam_toolbox で 2D SLAM
│   ├── 結果: 壁がシャープに閉じた地図 (占有 9,250 セル)。IMU yaw prior でも同等 (9,395)
│   └── 判定: ❌ R-Fans データは無罪 (2D で解けるのだから)
├── 段2: デッドレコニングと比べれば分かる?
│   ├── 実験: 車輪/IMU 姿勢で点群を開ループ積分 (マッチング補正なし)
│   ├── 結果: どの姿勢源でも渦状に塗れる — その場旋回のタイヤスクラブで yaw が狂う
│   └── 判定: この手法自体が品質判定に使えない (比較対象にならない)
├── 段3: IMU まわり (T_lidar_imu / プリインテグレーション) が主犯?  ← 当初の本命仮説
│   ├── 実験: IMU を使わない CT-ICP 構成で同じ bag を処理
│   ├── 結果: LIO より悪化 — z が対角に傾き (pitch ドリフト = 重力基準の喪失)、矩形が崩壊
│   └── 判定: ❌ 仮説棄却。IMU は問題を起こしておらず、むしろ垂直を守っていた
└── 段4: 定量化 — 軌跡の総延長を比較
    ├── 車輪 odom 48.5 m / GLIM-LIO 49.1 m (+1%) / GLIM-CT 307 m (6 倍超)
    └── 判定: LIO の距離推定は正確 = フロントエンドは壊れていない。
        「壊れた」のではなく「水平の拘束が足りず流れた」
```

結論: 主犯は **GLIM が車輪オドメトリを使わないこと × 環境の特徴の乏しさ (縮退寄り)**。
2D が解けたのは車輪 odom prior が前進方向をアンカーしたから (機構の一般論は
[第1章 1.5](01_3d_slam_basics.md) と第 3 章 3.5、2D 側の視点は
[slam_toolbox 読本 事例C](../slam_toolbox/06_case_studies.md))。

なお PROJECT_STATE の中間記録には「犯人は 3D 固有部」と**一度誤って絞り込んだ**痕跡が
残っている (08-12 (3))。段 3 で CT-ICP が悪化したことで初めて構図が見えた —
「仮説を殺す実験」を先に設計する価値の実例である。

### 修正 (未解決 — 対策候補 3 系統)

```
対策候補 (issue 記載 + 本書の対応章)
├── ① 車輪オドメトリ融合 (最有力・工事大)
│   └── ⚠️ glim_ros 標準ノードは /odom を publish するだけで購読しない (第2章 2.3)。
│       拡張モジュール (第2章 2.4) か C++ API での実装が必要
├── ② 撮り直し (工事ゼロ)
│   └── 特徴の多い経路・壁に寄る・ゆっくり旋回 — 縮退を環境側で避ける
└── ③ パラメータ調整 (中間)
    └── 第4章 4.11 の入口表。ループ系 (min_implicit_loop_overlap↓) と
        IMU noise の見直し。ただし現状は未チューニングの素の状態なので伸び代はある
```

### 教訓

- **「破綻」と「縮退による流れ」を区別する** — 距離 1% 差 (段 4) が決め手だった。
  総延長という単純な数字が仮説を 1 つ殺せる
- 仮説は「支持する実験」でなく「殺す実験」で検証する (段 3 の CT-ICP 比較)
- 導入評価は「対照系 (2D SLAM) と定量指標 (path 長)」を先に用意すると診断が速い

## 事例B

**潜伏していた時刻バグ — 消費者が現れて初めて発火する**

- 一次資料 (正): [タイムスタンプ読本 第6章 事例A・B](../timestamp/06_case_studies.md)。
  本書では GLIM 視点の要約のみ

### 症状

(実害が出る前に静的レビューで発見) LIO 切替の直前点検で、R-Fans ドライバに時刻の
欠陥が 2 件見つかった:

1. header.stamp が**スキャン末尾**基準 — 全点が実際より 0.16 s 未来の時刻を名乗る
2. per-point time が GPS 週秒の float32 直入れ (分解能 ~0.06 s に劣化) + フィールド名
   `timeflag` が GLIM の認識名 (`t`/`time`/`time_stamp`/`timestamp`) に含まれない

### 機構

興味深いのは「なぜ今まで無害だったか」である:

```
潜伏の構造
├── CT-ICP 時代: IMU を使わない = 点群の絶対時刻を誰も IMU と突き合わせない
│   └── stamp が 0.16 s ずれていても、点群内の相対時刻さえ揃っていれば CT-ICP は動く
└── LIO 切替: プリインテグレーションが「stamp の区間」の IMU を積分する (第3章 3.3)
    └── 0.16 s ずれ = 100 Hz の 16 サンプルが別区間に付け替わる。
        旋回 90°/s なら毎スキャン ~14° の歪みを注入 — 地雷が発火する条件が整った
```

### 修正

stamp をスキャン先頭基準に修正 + per-point time を相対化 + フィールド名を `time` に
改名 (2026-08-11、LIO 初回実行の前に完了)。おかげで事例A の診断では「時刻は容疑者から
除外済み」の状態で始められた。

### 教訓

- **構成変更 (CT-ICP→LIO) は新しい消費者を連れてくる** — 「今まで動いていた」は
  新構成での正しさを保証しない
- データ生産者の検証は「最も厳しい消費者」を基準に行う (時刻に最も敏感なのは LIO)

## 事例C

**運用の罠 3 連発 — viewer とダンプの仕様**

- 一次資料: `docs/claude/PROJECT_STATE.md` の 08-12 記録 (運用知見)。
  #1 の機構は `docs/issue/2026-08-15_offline_viewer_zenity_dialog_hang.md` で実証・精密化済み

### 症状と機構と対処 (3 件まとめて)

| # | 症状 | 機構 | 対処 |
|---|---|---|---|
| 1 | offline_viewer が進捗 0% でハング / Open New Map が無反応 | zenity の「Do optimization?」・フォルダ選択ダイアログは**起動して最前面にいるのに中身が描画されず不可視** (zenity 4 = GTK4 の GL 描画が CRD の X サーバ (DRI3 なし) で失敗)。pfd が回答待ちで永遠にブロック (2026-08-15 実証) | **`GSK_RENDERER=cairo` で解決済み** (compose の glim 環境変数、要コンテナ再作成)。非対話は従来通り `--export_path <out.ply>`。詳細: `docs/issue/2026-08-15_offline_viewer_zenity_dialog_hang.md` |
| 2 | dump の values.bin が欠けて offline_viewer が読めない | glim_rosbag を Ctrl+C 連打で止めると dump 書き込みが中断される | `glim_rosbag ... --ros-args -p auto_quit:=true` で bag 末尾到達時に自動終了させる |
| 3 | 走行中、古い場所の点群が薄く消えていくように見える | standard_viewer の**表示用間引き** (第4章 4.10)。カメラも機体追尾がデフォルト | 地図は消えていない。最終確認は dump を offline_viewer / PLY で見る |

### 教訓

- 「ハング」に見えたら、まず**見えないダイアログ・見えないプロンプト**を疑う。
  切り分けの最短手は `ps -ef` のプロセスツリー — 入力待ちの zenity 子プロセスが
  生きていれば確定 (2026-08-15 実証。ダイアログは「出ない」のではなく
  「最前面にいるのに描画されず不可視」のこともある — 詳細は issue 2026-08-15)
- 終了は必ず正規の経路で — 推定系のツールは終了時に成果物を書くことが多い
- ビューアの見た目は推定状態の証拠にならない。証拠は dump (第7章 7.5)
