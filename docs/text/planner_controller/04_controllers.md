# 第4章 controller の地図 — 経路を「どう」追うか

controller は planner の経路を受け取り、毎周期の速度を決める部品である。
第1章で見たとおり、Nav2 の controller は新しい経路を作らない。
それでも controller の種類によって、「止まるだけ」か「その場でかわせる」か、「回れる」か「下がれる」かが変わる。
この章では reRoBot の RPP を解剖し、他の controller と比べ、planner の保証と controller の動きの間にある隙間を測る。

## 4.1 一覧

| controller | 何をするか | 旋回 | 後退 | 本機 | つくば |
|---|---|---|---|---|---|
| **RPP** (Nav2) | 先読み点への弧を 1 本。当たれば止まる | 向きが 45° 超ずれたとき | 設定で可 | ○ 現行。避けずに止まる | 38 (Pure Pursuit 系) |
| DWB / DWA (Nav2) | (v, ω) の候補を多数試して採点 | 候補に入る | 設定で可 | ○ つくばで最多。調整項目が多い | 107 |
| **MPPI** (Nav2) | 数百本の軌道を試して最良を選ぶ | 可 | 可 | ◎ 本命候補。CPU が重い | 6 |
| TEB | 時間付きの帯を最適化 | 得意 | 得意 | △ ROS 2 版は保守が止まっている | 14 |
| Rotation Shim (Nav2) | 向きが大きくずれたら、まずその場で回してから本来の controller に渡す | 専用 | — | ○ RPP + Lattice の補助役 | — |
| Graceful (Nav2) | 姿勢へ滑らかに収束させる | 可 | — | △ ゴール付近向け | — |
| MPC 自作 | モデル予測制御 | 可 | 可 | × 実装の手間が大きい | — |

「つくば」は第3章 3.1 と同じ方法で数えた件数。

```
controller の 2 系統
├── 幾何追従 (RPP・Pure Pursuit) .... 経路の上の点に向かう。計算が軽い。障害物は「止まる」ことでしか扱えない
└── 軌道サンプリング (DWB・MPPI・TEB) . 候補の軌道を試して障害物を避ける。計算が重い。経路から外れてもよい度合いを重みで決める
```

## 4.2 RPP の解剖

RPP (Regulated Pure Pursuit) は reRoBot の現行 controller である (`nav2_params.yaml:93`)。

### 4.2.1 先読み点 (carrot)

```
先読み距離 L = clamp( 実速度 × lookahead_time, min_lookahead_dist, max_lookahead_dist )
             = clamp( v × 1.5 s, 0.6 m, 0.9 m )      (reRoBot、:101〜:103)
```

停止中や低速 (v < 0.4 m/s) では L が下限の 0.6 m に張り付く。
11-03 までは下限が 0.3 m で、止まると L が 0.3 m に縮んでいた (事例 A の自己保持の原因)。
計算は `nav2_regulated_pure_pursuit_controller/src/regulated_pure_pursuit_controller.cpp:140〜141`。

### 4.2.2 曲率

先読み点がロボット座標で (x, y) にあるとき、今の位置から先読み点を通り今の向きに接する円弧の曲率は

```
κ = 2y / (x² + y²) ≈ 2y / L²        (regulated_pure_pursuit_controller.cpp:158)
```

L が半分になると、同じ横ずれ y でも曲率は 4 倍になる。

| 横ずれ y | L = 0.3 m | L = 0.6 m |
|---|---|---|
| 0.10 m | 半径 0.45 m | 1.8 m |
| 0.19 m | 0.24 m | 0.95 m |
| 0.30 m | 0.15 m | 0.60 m |

### 4.2.3 衝突の先読み

`use_collision_detection` が有効なとき、RPP は毎周期次の順で検査する
(`nav2_regulated_pure_pursuit_controller/src/collision_checker.cpp:56〜105`)。

```
isCollisionImminent
├── 1. 現在の姿勢の footprint が lethal に触れていたら即「衝突」 (:56)
├── 2. 今の (v, ω) で footprint を少しずつ動かし、各姿勢で lethal に触れるか調べる
│      ├── 刻み: 直進なら 1 セル進む時間、その場旋回なら外接円が 1 セル動く時間 (:72〜:85)
│      ├── 打ち切り: max_allowed_time_to_collision_up_to_carrot (2.0 s、:116)
│      └── 打ち切り: 先読み点の距離を越えたら終了 (:105)
└── 3. どこかで触れたら「collision ahead」 → 速度 0
```

ここから 3 つの性質が出る。

- **前方停止距離 = 先読み距離**。打ち切りが先読み点なので、前に立つ人の手前 L (0.6 m) で止まる。
- **現在姿勢が触れていたら永久に 0**。旋回も後退も同じ検査を通るので、既に縁が lethal に乗っている姿勢からは出られない。
- **検査は弧の上の姿勢**。経路上の姿勢ではない (4.6)。

`failure_tolerance: -1.0` (`nav2_params.yaml:73`) にしてあるので、衝突判定が続いても FollowPath は失敗にならず、待ち続ける。
これは「前に人がいれば待つ」ための設定だが、凍結したときは人が動かすまで解けない。

### 4.2.4 その場旋回モード

先読み点の方位が 45° (`rotate_to_heading_min_angle` 0.785 rad、`nav2_params.yaml:119`) を超えると、RPP は弧ではなくその場旋回に切り替える
(`regulated_pure_pursuit_controller.cpp:243`、`shouldRotateToPath` :305〜316)。

```
その場旋回モード
├── 前進 0、角速度 ±1.0 rad/s
├── 衝突検査は回転の掃引 (外接円 0.62 m の範囲)。先読み距離は関係しない
└── 後ろの角が 0.6 m の円を描くので、横 0.45 m の物体があると回れない
```

NavFn の時代、角では経路が 45° 以上折れるので、RPP はこのモードで「止まって回る」動きをしていた。
Smac の経路は常に自機の向きから始まるので、このモードが発動しない。
「Smac にしてから急旋回しなくなった」の半分はこれである (残り半分は Hybrid にその場旋回が無いこと)。

### 4.2.5 減速

曲率半径が `regulated_linear_scaling_min_radius` (0.9 m、`nav2_params.yaml:106`) より小さいと速度を落とす (下限 0.25 m/s)。
急な経路ほど角で遅くなる。

## 4.3 DWB と MPPI

どちらも「候補を試して選ぶ」controller である。

```
DWB (Dynamic Window)
├── 今の速度から加速度の範囲で届く (v, ω) を格子状に並べる (例: 20 × 20)
├── 各 (v, ω) で 1〜2 s 先までの軌道を作り、critic (障害物・経路への近さ・ゴールへの向き…) で採点
└── 最良の (v, ω) を出す。ω のみ (その場旋回) も候補に入る

MPPI (Model Predictive Path Integral)
├── 制御列 (数 s 分の v, ω の時系列) を乱数で数百〜数千本作る
├── 各軌道を critic で採点し、良い軌道ほど重く平均して次の制御列にする
└── 障害物の手前で自然にかわす・回る・下がる。CPU は重い (T480s で要計測)
```

どちらも出力は速度で、/plan を書き換えない。
ただし「経路から外れてよい」ので、近くの障害物をその場でかわせる。第1章 1.3 の「local は止めるだけ」が成り立たなくなる。

## 4.4 TEB

Timed Elastic Band は、経路をゴムひものように最適化し、時間情報を付けて追う。
差動二輪の旋回・後退の扱いが上手く、ROS 1 では定番だった。
ROS 2 版はコミュニティの移植で、Jazzy での保守は止まっている。

## 4.5 Rotation Shim

Rotation Shim は単独の controller ではなく、他の controller を包む補助役である。

```
Rotation Shim + RPP
├── 経路の向きとロボットの向きが閾値以上ずれていたら、Shim がその場旋回する
└── 揃ったら RPP に渡す
```

Lattice が「ここで回れ」という経路を出したときに、回転を確実に実行させる役になる。
RPP 単体の旋回モードと違い、経路の各点の向き (Lattice は持っている) を基準にできる。

## 4.6 planner の保証と controller の動きの隙間

向き付きの planner (Smac) は、**経路上の各姿勢**で四角が当たらないことを保証する。
しかし RPP は経路の上を走らない。毎周期「今の向きに接し、先読み点を通る円弧」を引き直し、その弧の上を走る。

例: 経路 = 直進 0.15 m → 半径 0.3 m の右弧、先読み 0.6 m。RPP の弧は半径 0.5 m。
同じ前進距離で、車体の左端 (後ろの左角を含む) がどこまで左に出るかを比べる。

| 前進 | 経路上の姿勢: 向き / 左端 | 弧上の姿勢: 向き / 左端 | 差 |
|---|---|---|---|
| 0.1 m | 0° / 0.325 m | 11° / 0.410 m | +8.5 cm |
| 0.2 m | 10° / 0.401 m | 23° / 0.458 m | +5.7 cm |
| 0.3 m | 29° / 0.493 m | 34° / 0.469 m | −2.4 cm |
| 0.4 m | 48° / 0.498 m | 46° / 0.441 m | −5.7 cm |

弧は経路より早く曲がり始めるので、出だしで後ろの角が最大 8.5 cm 外に出る。
その姿勢は planner の検査対象ではないので、経路と物体の余裕が 8 cm を切ると、RPP 自身の衝突検査で止まる。

```
planner の保証が controller まで届かない所
├── 弧と経路の差 ......... 出だしで最大 8.5 cm (経路が急なほど大きい)
├── 地図の差 ............. planner は global (地図あり 0.1 m)、controller は local (live 0.05 m)。reRoBot では約 0.15 m ずれる
├── 更新の差 ............. global 1 Hz・再計画 3 s と、local 5 Hz・制御 20 Hz
└── footprint の差 ....... global だけ楽観 footprint にしていた期間 (11-04〜11-06) は 7.5 cm
```

この隙間は衝突の危険ではなく**停止の危険**である。最終判定は controller が実寸・live で行うので、隙間があると「planner は通れると言ったのに controller が止める」形で現れる。
隙間を小さくする手は 3 つある。

| 手 | 効果 | 代償 |
|---|---|---|
| 先読み距離を短く | 弧が経路に近づく | 停止中の曲率が上がる (事例 A に戻る) |
| 経路の曲率変化を緩く (Smac の R を大きく) | 出だしの差が小さい | 曲がりが緩くなる (事例 C の体感) |
| 経路を正確に追う controller (MPPI) | 差そのものが消える | CPU と再調整 |

## 4.7 この章のまとめ

```
├── RPP は「先読み点への弧 1 本」。避けない、当たれば止まる。現在姿勢が触れていたら永久に 0
├── 先読み距離は前方停止距離と曲率の両方を決める。止まると下限に張り付く
├── RPP のその場旋回は先読み点が 45° 超ずれたときだけ。Smac の経路では発動しない
├── DWB / MPPI は候補を試すので、その場でかわし・回り・下がれる
├── Rotation Shim は Lattice の「回れ」を確実に実行させる補助
└── planner の保証は経路上の姿勢まで。弧・地図・更新の差の分だけ controller が止める余地が残る
```
